# 零、核心原则与心智模型

## 0.1 五条核心原则

〔指南〕五条原则贯穿全部设计判断，取舍不下时回来对照：

| 原则 | 一句话 |
|---|---|
| **准确** | 感知对话上下文，响应与界面应与用户当下需求紧密相关，不做通用套话 |
| **克制** | 每次交互聚焦一个清晰操作/结果，信息与界面精简到只支持当前上下文 |
| **轻量** | 工具应快速轻便，增强对话而非拖慢对话 |
| **可信** | 清晰说明能力边界与执行状态，过程可控、结果可验证 |
| **普适** | 支持不同能力/设备/熟练度的用户完成核心任务（见 [5.3](#53-无障碍与包容性)） |

## 0.2 产品心智模型与四层信息分层

〔通用契约〕**智能体产品不是聊天软件。** 聊天软件的核心是「消息」，智能体产品的核心是**「委托 → 执行 → 交付」的可信闭环**。

用户的真实诉求有三层，优先级从高到低：

1. **它做完了吗**（结果）
2. **它是怎么做的、可信吗**（过程）
3. **产物在哪、能不能用**（交付）

界面由此分成四个信息层。**任何新能力都必须先归位到其中一层**，不能归位说明能力定义还没想清：

| 层 | 职责 | 失职表现 | 组件目录 |
|---|---|---|---|
| **委托层** | 让用户低成本说清要什么、带什么上下文、由谁来做 | 用户不知道能带什么进来 | [components/delegation/](components/delegation/) |
| **对话层** | 承载语义：我问了什么、它答了什么 | 过程噪音淹没结论 | [components/conversation/](components/conversation/) |
| **过程层** | 建立可信度：拆解、动作、依据 | 只有 Spinner，无法判断是否可信 | [components/process/](components/process/) |
| **产物层** | 让产出可查看、可带走 | 结论提到了某份资料，但打不开 | [components/artifact/](components/artifact/) |

**最重要的一条：过程层服务于信任，不服务于炫技。** 能折叠、能跳过、能只看结论，是过程层的设计前提，不是妥协。

> 组件目录的分组方式与本节的四层模型同构，另加壳层（[shell/](components/shell/)）与注册表（[registry/](components/registry/)）两组基础设施。走完[第七章决策流程](#七扩展新能力的决策流程)第 1 问后可直接落到对应目录。

# 一、能力识别与引导

## 1.1 能力识别

〔指南〕定义智能体"是谁"：

- **命名**：优先功能导向名称（"合同审核助手""数据分析助手"）。ToC 产品可用品牌化名称，但**不得使用真实人名、暗示真人身份或造成品牌混淆**。
- **头像/标识**：优先虚拟形象、抽象图形或统一 AI 标识，**避免真人头像**。
- **描述**：明确告知能做什么、不能做什么。
- **语气**：专业场景严谨克制，生活场景轻松自然。

**禁止项**：
- ❌ 给 AI 起人名、设定性别、用真人照片。
- ❌ 隐瞒 AI 身份让用户误以为在和人对话。
- ❌ 角色设定与实际能力不匹配（声称"全能"但只能简单问答）。

## 1.2 首屏引导

〔指南〕用户进入后应快速知道"它能做什么、我可以从哪里开始"：

- 首次进入展示**一句欢迎语 + 核心能力概述 + 3–5 个推荐操作**。
- 推荐操作必须**具体、可点击**（例："总结这份会议纪要"）；**禁止**"有什么可以帮你"等模糊引导语。
- 空状态展示能力卡片、分类入口或示例任务；**禁止**空白页面或仅显示 Logo。

〔沉浸式契约〕首屏推荐分两层，且有联动规则：

- **专家推荐**（横向按钮行）+ **指令推荐**（卡片，桌面分页 / 移动横向滚动）。
- 点击初始推荐指令 → 同时把对应专家和提示词加入输入区，**两层推荐整体隐藏**；删除专家后恢复初始状态。
- 选中专家后 → 专家推荐行消失，下方切换为该专家的**纵向**推荐指令列表；点击纵向指令填入提示词并隐藏该列表，专家保留在输入区。
- 推荐卡片的专家名固定单行高度，指令名固定两行高度且顶部对齐；**只有实际超过两行时才显示完整内容 Tooltip**。

## 1.3 智能体身份开场

〔通用契约〕**每一轮回复都从「头像 + 名称」开始**，紧接执行过程。

- 指定了专家 → 专家头像 + 专家名。
- 未指定 → 产品身份头像 + 产品名。
- 产品身份在侧栏顶部和对话流中**必须是同一套视觉**，改名改头像只改一处。

**为什么**：多智能体产品里"这句话是谁说的"是理解成本最高的问题，固定的开场位置把它降为零。

**归属边界**（与 [3.1](#31-意图输入) 的上下文三分配套）：选专家等于"指定谁来执行"，属于**智能体侧**，**不进用户消息**。

# 二、界面形态与空间

## 2.1 界面形态选型

〔指南〕界面形态回答"用户主要在哪里完成任务"。**选型由主要任务决定，不由是否接入 AI 决定。**

| 形态 | 定义 | 区块结构 | 典型场景 | 本 skill 覆盖 |
|---|---|---|---|---|
| **沉浸式 Agent** | 具备独立运行能力的专属界面框架，对话流是主工作区 | 左侧对话管理菜单栏（非必需）+ **中间对话流** + 右侧独立面板 | 通用助手、客服、知识问答 | ✅ 完整脚手架，细则已实测 |
| **助手式 Copilot** | 通过侧边或悬浮窗口提供辅助，不干扰主任务连续性，AI 是配角 | 左侧资源/项目区 + **中间主工作区** + 右侧对话辅助区 | IDE、设计工具、BI、合同审阅、低代码搭建 | ⚪ 轻量骨架，细则未实测 |
| **嵌入式 Embedded** | 深度集成于产品原有界面，高频操作环节即时触发 | 悬浮卡片 / 划词工具栏 / 右键菜单 | 翻译、文本润色、局部增强 | ⚪ 不固化模板，按 [2.4](#24-嵌入式设计约束) 现场设计 |

### 选型决策树

```
主要任务是什么？（由任务决定，不由"是否接入 AI"决定）
├─ 用自然语言表达目标、等待结果，需要专注连贯环境
│     → 沉浸式 Agent（左菜单/中对话流/右面板）  例：通用助手、客服、问答
├─ 围绕画布/代码/表格/设计稿/业务对象持续操作，AI 辅助但不想离开主工作区
│     → 助手式 Copilot（左资源区/中主工作区/右对话辅助区；或浮窗/抽屉）  例：IDE、设计、BI、合同审阅
└─ 在现有工作流里要轻量即时的 AI（翻译/润色），无需独立对话空间
       → 嵌入式 Embedded（划词工具栏/悬浮卡/右键菜单）  例：文档、表格内嵌
```

**一句话选型**：AI 是主角还是配角？配角就别抢主工作区。

**反例**：为塞 AI 侧栏把合同正文压到一半宽 → 违反"不为放置 AI 入口压缩主要业务对象"。

## 2.2 响应式与空间分配

### 核心原则

〔指南〕
- **优先保障主任务**：沉浸式优先保对话流，助手式优先保主工作区。
- **保留上下文**：布局变化不应导致会话、输入内容、打开对象丢失。
- **收纳辅助区**：空间不足时，优先收起左侧导航，再将右侧面板转为覆盖式或全屏式。
- **简化小屏体验**：屏幕越小，越应减少并列区域和复杂浮层。

**降级顺序铁律：先收左侧菜单栏 → 再把右侧面板降级为覆盖/全屏。**

### ⚠️ 两组数值的关系（必读）

指南与沉浸式实测给出的断点和宽度**不一致**，这不是矛盾，是层级不同：

| | 断点 | 区域宽度 | 性质 |
|---|---|---|---|
| 〔指南〕 | 1024 / 768px | 菜单栏 240、对话流 440、工作面板 320 | 指南原文明示**"最小极限数值，但不是强制标准，不同产品可根据实际业务复杂度增加最小宽度的设定"** |
| 〔沉浸式契约〕 | 980 / 740 / 659px | 侧栏 240、对话区 `clamp(420px, 50%, 800px)`、独立面板 min 320 | 真实实现中调优并验证过的契约 |

**取用规则：**
- **沉浸式**：用沉浸式契约的数值（下方 2.2.1）。它满足指南的下限声明（440 → 420 是唯一低于指南的一项，属于指南允许的产品自主调整范围，因为对话区另有 800px 上限保证可读性）。
- **助手式 / 嵌入式**：沿用指南数值（下方 2.2.2），因为尚无实测契约。
- 新形态或大改布局时，先满足指南下限，再依据实测调优并回写本节。

### 2.2.1 沉浸式契约

〔沉浸式契约〕

| 总宽度 | 侧栏 | 产物面板 |
|---|---|---|
| ≥ 980px | 停靠 240px | 参与分栏 |
| 740 – 980px | 转抽屉（320px） | 参与分栏 |
| < 740px | 抽屉 | **全屏** |
| < 659px（移动） | 抽屉 | 全屏 |

**对话区与产物面板的分配原则：对话区有阅读宽度上限，富余空间全给产物面板。**

- 对话区 `clamp(420px, 50%, 800px)`，产物面板承接剩余、下限 320px。
- 800px 上限来自正文自身阅读宽度（内容 `max-w-3xl` = 768px + 左右 padding），再宽只是留白；而网页和文档预览越宽越好读。
- **用 CSS 约束表达，不用脚本测量容器**——窗口缩放要连续变化，不是跳档。
- 用户拖过分隔线后改为显式宽度，但缩窗时必须动态限制为 `calc(100% - 420px)`，不让历史宽度挤压对话区。
- 980px 与 740px 两个临界点正好落在 420 / 320，不会溢出。

默认分栏实测尺寸：

| 总宽度 | 侧栏 | 对话区 | 产物面板 |
|---|---|---|---|
| 2560px | 240 | 800（触顶） | 1520 |
| 1920px | 240 | 800（触顶） | 880 |
| 1440px | 240 | 600 | 600 |
| 1280px | 240 | 520 | 520 |
| 1100px | 240 | 430 | 430 |
| 980px | 240 | 420（触底） | 320（触底） |
| 900px | 抽屉 | 450 | 450 |
| 740px | 抽屉 | 420（触底） | 320（触底） |
| < 740px | 抽屉 | — | 全屏 |

移动端（< 659px）：**一次只显示一个主要区域**，中间内容不保留桌面端最小宽度约束；页面高度用**动态视口高度**（`dvh`），避免底部空白；输入框、停止生成、返回、关闭面板等关键操作稳定可达。

**窄屏已强制全屏且没有非全屏形态时，隐藏全屏按钮**，不要留一个点了没反应的死按钮。

### 2.2.2 助手式 / 嵌入式（指南下限）

〔指南〕

| 设备 | 断点 | 要求 |
|---|---|---|
| 桌面端 | ≥ 1024px | 多栏并列；主工作区保持可读可操作 |
| 平板端 | ≥ 768px | 左侧菜单默认收起（抽屉）；双栏或模式切换 |
| 移动端 | < 768px | 单栏任务流；面板升级为全屏/底部弹层 |

| 区域 | 建议最小宽度 | 低于该宽度时的行为 | 降级顺序 |
|---|---|---|---|
| 菜单栏 | 240px | 收起，通过触发按钮展开为抽屉 | 1（最先） |
| 对话流 | 440px | 助手式：收起为抽屉 | 2 |
| 工作面板 | 320px | 助手式：升级为全屏（需保留触发对话流的按钮） | — |

**触发条件**：① 视口 < 三区最小宽度之和且菜单栏展开 → 收起菜单栏；② 菜单栏已收起且视口 < 对话流+面板最小宽度之和 → 面板升级为覆盖式弹层或全屏。

### 2.2.3 每次响应式改动的必查宽度

桌面宽屏 → 侧栏收起 → 约 700px 窄桌面 → 659px 以下移动端。

## 2.3 助手式布局子类型

〔指南〕

| 子类型 | 特征 | 适用 | 不适用 |
|---|---|---|---|
| 浮窗 | 可拖拽到任意位置、可缩放，遮挡原内容 | 无需与主页面对照操作 | 需要对照操作的场景 |
| 浮层抽屉 | 压缩原页面空间，占据中右/左一部分，与主页面共用顶部导航，内容无遮挡 | 需与主页面信息对照、或频繁交互 | — |
| 侧边抽屉 | 压缩原页面空间，与主页面左右布局 | — | 主页面信息密度大、横向空间紧张 |

**选型建议**：默认优先三栏并列（信息密度可控、不遮挡）；已有产品的局部增强更适合浮层抽屉；纯轻量辅助、不长期占用布局空间时用浮窗。

## 2.4 嵌入式设计约束

〔指南〕嵌入式不固化模板，但现场设计时必须遵守：

- **灵活触发**：悬浮卡片 / 划词工具栏 / 右键菜单形式，低覆盖容器，随时可触发。
- **焦点规则**：功能卡片出现时，原光标焦点不得丢失。
- **上下文保留**：卡片关闭后，宿主编辑器须保持完整。
- **权限最小化**：仅申请完成当前任务所需的最小宿主权限（如当前选中文本读取权限）。

# 三、场景链路

以下环节适用于沉浸式与助手式的对话流部分。

## 3.1 意图输入

〔指南〕意图输入由**提示词、上下文、能力**三类要素构成，应支持独立输入、组合使用、随时编辑，发送前清晰呈现完整构成。

| 要素 | 内容范围 | 设计要求 | 推荐交互 |
|---|---|---|---|
| 提示词 | 目标/要求/约束/输出格式 | 支持多行编辑、连续补充、撤销修改、草稿保留；除键盘外支持语音转写；发送前可校对修改 | 键盘输入 / 语音输入 |
| 上下文 | 附件/引用/知识库/记忆等 | 明确来源、作用范围、有效期限、权限状态；已添加内容以标签/卡片展示，支持预览/替换/移除；区分**临时上下文**与**可持续使用的记忆** | `@` 呼出选择器 / 添加按钮或菜单 |
| 能力 | 子智能体/技能/工具等 | 提供推荐 + 主动选择两种方式；调用前展示名称/用途/适用范围/可能影响；已选能力须显式呈现，避免用户误以为会自动调用所有能力 | `/` 呼出选择器 / 添加按钮或菜单 |

补充要求：
- `@` / `/` 呼出的选择面板需**可搜索、可分组、支持最近使用记录**，选中后以可识别标签插入输入区域。
- 能力快捷入口可给推荐项，但**推荐项是快捷选择，不能替代用户对具体能力的控制**。
- 占位提示随场景动态变化；语音转写/文件上传/上下文解析等异步操作要展示处理中/成功/失败状态。
- 涉及敏感数据、外部系统或高风险操作的上下文/能力，**发送前补充权限、范围或审批提示**。

### 3.1.1 上下文与能力按「能不能内联」三分

〔通用契约〕这是指南三要素在**呈现位置**上的细化。呈现方式由**它是不是消息语义的一部分**决定：

| 类别 | 位置 | 理由 |
|---|---|---|
| 文件库 / 最近的对话 / 技能 | **气泡内**内联标签，位置由文本中的引用位置决定 | 它是句子的一部分：「参考〔某文件〕整理」 |
| 本地上传文件 | 气泡**上方**独立附件卡片 | 它是随消息携带的实体，不是句子成分 |
| 智能体（专家） | **不在用户消息里**，作为智能体身份出现在回复侧（见 [1.3](#13-智能体身份开场)） | 选专家是"指定谁来做"，属于执行者，不是用户说的话 |
| 连接器 | **不进消息流** | 它只决定这一次请求怎么执行；过程层的「调用连接器 X」已经体现 |

**一致性铁律**：同一种上下文/能力，在侧栏、输入区、菜单、已选状态、消息流中**必须是同一个图标**。图标不一致会被读成不同东西。

〔沉浸式契约〕`/` 引用「能力」，`@` 引用「上下文」；两者只收录**能以标签形式插入输入框**的类型——专家、连接器、本地上传文件不在其中（前两者在底部操作行，后者在输入框上方附件区）。同一页面内 `/` 与 `@` 的展开方向必须一致，不做按内容高度的自动翻转。

## 3.2 执行过程透明

〔指南〕以**决策过程可见、加载状态可感、结果来源可查**为原则，展示"正在发生什么"。**不展示模型内部原始思维链或系统提示词。**

三个层级：

| 层级 | 含义 |
|---|---|
| **L1**（状态层） | 整轮任务的状态摘要 + 消耗时长（"任务耗时 18 秒" / "任务进行中… 1 分 36 秒"） |
| **L2**（任务层，非必须） | **规划任务**。只有当智能体真的先拆解、再分头执行时才存在 |
| **L3**（执行层） | 实际执行步骤，渐进式展示步骤、工具调用、检索范围与阶段性结果 |

### 3.2.1 结论优先，过程可折叠

〔通用契约〕结论永远在最容易读到的位置。

- **只有「正在执行中」的过程默认展开**——此时用户没有结论可读，过程就是唯一有效信息。
- **已完成的过程默认收起**，只留一行 L1 状态摘要。
- 用户主动展开是查证行为，不是默认路径。

### 3.2.2 层级必须反映任务真实复杂度，绝不为完整性硬造

〔通用契约〕**判定规则：**

| 任务特征 | 结构 |
|---|---|
| 单一目标，线性几步 | L1 → L3（扁平） |
| 极简确认类，无中间产出 | L1 → L3，且隐藏摘要与时间线 |
| 多个可独立描述的子目标，需分头执行再汇总 | L1 → L2 → L3 |

约束：

- **L2 不允许嵌套 L2。** 规划刷新时替换同级 L2 列表，不要再包一层汇总任务。
- **有 L2 就必须有可查看的 L3**，空 L2 是无意义的层级。
- L2 展开后的 L3 使用**扁平样式**，不重复 L2 的状态圆点、粗标题和竖向时间线——否则视觉上会读成「L2 里又有 L2」。
- 执行中的 L2 默认展开；已完成的 L2 默认收起只显示标题。
- L2 的展开/折叠箭头紧跟标题文字，不固定在整行最右侧。
- L2 的完成总结只显示在展开内容的最底部，不显示在 L2 标题下方。

**为什么严格**：层级是给用户的复杂度信号。为一个三步任务套上规划层，等于谎报复杂度，用户下次就不再信任这个信号了。

### 3.2.3 有产物的动作才做成可点击资源

〔通用契约〕执行步骤里的具体操作用 Badge 呈现，但**能不能点，取决于有没有用户可查看的产物，而不是动作类型**。

| 类型 | 可点击 |
|---|---|
| 知识检索、网页浏览、文件读取 | 是，打开对应容器 |
| 技能调用、接口调用、脚本执行、内部状态查询、连接器调用 | 否，纯过程说明 |

**反例**：把「调用技能 X」做成按钮，点开是一段没有信息量的日志。这会训练用户放弃点击所有 Badge。

〔指南〕工具调用要以**用户可理解的方式**呈现（"正在读取 4 份文档"而非接口名）。

### 3.2.4 深度思考面板的使用边界

〔通用契约〕深度思考**不是固定层级，不能出现在每个执行过程里**。只在三种场合出现：

1. 协调型智能体的深度思考。
2. 复杂任务开始阶段的规划推理。
3. 执行遇到问题后的自纠错推理。

非流式时默认收起，运行中默认展开。

**为什么限制**：思考过程是「解释成本」。到处都有就等于没有重点，用户会整体跳过。

## 3.3 追问澄清

〔指南〕用户意图模糊时，**智能体应主动追问，而不是猜测执行。**

**需要澄清的情况**：输入过短且可能对应多种操作；关键参数缺失导致任务无法执行（"帮我发邮件"没有收件人）；出现歧义词（"最新的""重要的""那个文件"）；操作风险较高可能影响真实业务数据。

**设计要求**：

| 规则 | 内容 |
|---|---|
| 追问数量 | 每次只问关键缺口，**不要一次性甩出所有缺失项** |
| 呈现方式 | 待澄清事项 **≤2 → 自然语言追问**；**>2 → 澄清表单卡片**；事项需要枚举 → 卡片 |
| 表单录入 | **选择优于输入**；可基于追问事项生成可行选项，按需提供"其他""都不适用" |
| 跳过机制 | 任何追问方式都必须允许"跳过/忽略" |
| 等待状态 | 追问期间对话入口（如对话列表）须有明确"等待"状态呈现，直至用户完成澄清提交 |
| 意图修正 | 用户应能随时修正已表达的意图 |

**对话过程总体原则**：简洁（默认回答当前问题，要求详细才展开）、连贯（保持上下文，不要求重复已提供信息）、可控（用户能停止/修改/重试/继续追问）。

### 3.3.1 向智能体索要结构化信息，用表单而不是追问

〔通用契约〕当指令缺少继续执行所需的结构化信息（日期、事由、偏好），推送**澄清表单卡片**，而不是用自然语言反复追问。

- 必填项未齐前**提交禁用**。
- **提交后字段转只读摘要**，操作区消失，标题栏显示「已提交」，卡片仍可展开查看记录。
- 表单必须用与产品其它表单**同一套基础组件**，日期这类控件**不要退回浏览器原生选择器**——原生控件在跨平台下视觉和交互都不受控。

**为什么用表单**：多个字段用对话来回问，会产生 3~5 轮无信息量的往返，且用户无法一次看到「还差什么」。

**卡片硬约束**：无 Tabs/Menu 等深层导航，无内部滚动；字段 **≤10** 且优先单列；仅对**阻断性内容**设必填；操作按钮 **≤3、主按钮 ≤1**，放卡片底部。

## 3.4 操作确认

〔指南〕任务经[风险分级](#51-风险分级与人工接管)判定为需确认时，**应暂停执行**，清晰展示待执行操作及影响，获得用户明确确认后才继续。展示方式：Markdown（轻量确认）/ 确认卡片（强确认）。

**确认卡片硬约束**：

- 无 Tabs/Menu 等深层导航，无内部滚动。
- 信息字段 **≤10**，所有内容**直接可见**，不通过"悬停/点击"触发。
- 操作按钮 **≤3、主按钮 ≤1**，放底部。
- **不重复 AI 已用文字表达的信息**——卡片只问决策。
- **高风险场景**字段必须含**对象 / 动作 / 影响范围 / 后果 / 操作人**，且**不得用自然语言确认代替**。

执行结果必须**回写对话流**（"✅ 已为你创建 4 个日程（含 1 处冲突待你确认）"）；跳过则不执行、保留结果供后续再确认。

## 3.5 结果呈现与产物容器

〔指南〕通过结构化、可交互界面组件，将生成内容以文本/图片/表格/代码/卡片等多模态形式展示。

### 3.5.1 Markdown（内联响应）

对话流内最基础的富文本响应格式，适合文本/列表/标题/引用/代码块/图片。

**要求**：结构清晰，善用分段/列表/加粗；单次输出不宜过长，长内容拆分或生成制品；引用链接准确且与上下文相关；**不重复用户已知信息，聚焦增量价值**。Markdown 正文统一由排版层处理，不在业务组件里逐个元素设样式。

### 3.5.2 交付物必须是一等公民

〔通用契约〕如果一轮任务的目的是产出东西，那么**结论文字不算交付**，必须给出可点击的产物附件。

- 对话流内**只展示摘要**：文件名、类型、简短描述或生成时间。**不在对话流内展示完整产物内容。**
- **用户附件右对齐**（跟随气泡），**智能体交付物左对齐**（跟随回复），两者共用同一套附件卡片和打开链路。
- 执行过程里「已生成 X」的 Badge 与最终交付附件**必须指向同一个产物**。两个入口打开不同东西，等于告诉用户系统内部不一致。
- 面板内操作结果应**同步回对话流**（面板中修改文档后，对话流显示"已保存修改"）。
- 面板定位为**上下文工作区**，不承载全局导航和系统设置。

### 3.5.3 产物容器区分「并排比对」与「专注查看」

〔沉浸式契约〕**判定问句：用户会不会一边看它一边看对话？**

| 需求 | 容器 |
|---|---|
| 需要与对话并排、可能多个同时存在 | **右侧面板的容器 Tab**（检索结果、网页、文档预览） |
| 需要全屏专注、只看一个 | **蒙层查看器**（图片） |

容器 Tab 的规则：

- 同一产物**重复打开只切换 Tab**，不重复新建（按内容判重：检索按查询词、浏览器按 URL、文件按文件名）。
- 容器内的跳转（检索结果 → 打开某条网页）属于**同一容器内导航，复用当前 Tab**，不新开。
- **容器专属操作放在各容器自己的操作栏**，面板顶部只保留全屏和关闭两个全局操作。
- 只有一个 Tab 时不显示关闭按钮；多 Tab 时激活 Tab 常显关闭按钮，非激活 Tab 悬停或聚焦才显示。关闭最后一个 Tab 等于关闭面板。
- **切换对话必须立即清理上一对话的产物面板**，不能短暂展示旧内容。

## 3.6 消息操作

〔指南〕每条消息末尾提供统一操作栏：

- 智能体消息：**复制、点赞/点踩、朗读、重新生成、分享**。
- 用户消息：**编辑、重新发送、复制、删除**（按产品能力）。
- 两类消息的操作按**消息归属和当前状态**分别设计，避免无意义或容易误触的操作。
- **高频操作直接展示，低频/扩展功能收纳至"更多"菜单**。
- 所有操作配备清晰图标、悬停提示、点击反馈，按消息状态动态显示可用项。
- 重新生成/分享等影响后续流程的操作，须明确反馈执行结果。

〔通用契约〕具体行为：

- **悬停操作栏用常驻占位 + 透明度切换，不要条件渲染 DOM**——后者会让鼠标移入移出时下方内容跳动。
- **复制**：图标原地变对勾，几秒后恢复。**不弹 Toast**（消息级操作太频繁）。
- **点赞/点踩互斥**。
- **点踩打开反馈弹窗**，选原因或填补充说明；**点了提交才置为已反馈态**，取消不改状态。

## 3.7 后续引导

〔指南〕
- 每次交互结束后，可提供 **2–4 个推荐追问**。
- 推荐内容应基于**当前上下文生成**，而非固定话术。
- 用户可忽略推荐，直接输入新问题。

**不应触发推荐追问的场景**：
- ❌ 用户已明确结束对话。
- ❌ 用户表达不满、投诉或负面情绪。
- ❌ 当前任务失败且尚未给出恢复路径。
- ❌ 高风险操作刚刚完成，需要用户先确认结果。

**过度设计反例对照**：

| 场景 | ❌ 过度设计 | ✅ 正确做法 |
|---|---|---|
| "今天天气怎么样" | 回答后主动推荐景点、穿衣建议、空气质量、一周预报 | 只回答今天天气，其余作为可选追问 |
| "总结这份文档" | 总结后主动分析优缺点、改进建议、延伸阅读 | 只提供总结，其余作为推荐追问 |
| "某产品参数" | 回答参数后主动推荐竞品对比、购买链接、用户评价 | 只回答参数，推荐追问与参数相关 |

> 注意区分：本节是**轮次末尾**的推荐追问；[1.2 首屏引导](#12-首屏引导)的 3–5 个推荐操作是**首屏空状态**的，两者不是同一个东西。

## 3.8 一轮对话的结构与间距契约

〔通用契约〕自上而下的固定结构：

```
[用户附件]            ← 右对齐，仅本地上传
[用户气泡]            ← 内联标签在气泡内
[用户操作栏]          ← 常驻占位，默认透明，悬停显现
─── 20px ───
[智能体身份]          ← 头像 + 名称
─── 8px ───
[执行过程 L1]         ← 默认收起
─── 20px ───
[智能体正文]
[交付物附件]          ← 左对齐
[智能体操作栏]
```

契约：

- **消息块之间 20px；执行过程到正文 20px；身份到执行过程 8px。**
- 用户消息内部（附件、气泡、操作栏之间）保持 **8px**。
- 普通回复与「表单提交后的续流程」使用**同一个回复块结构**。任何一处单独调间距，都会立刻产生视觉漂移。

# 四、状态与反馈

## 4.1 四种状态语言

〔通用契约〕四种状态**各有唯一表达，且不互相借用**：

| 状态 | 表达 |
|---|---|
| **执行中** | Spinner + 运行中 L1 标题的扫光动画（shimmer） |
| **等待用户回复** | 警示色标签 + 「需要你的回复」 |
| **完成未读** | 绿点，进入即消 |
| **已提交**（表单） | 标题栏右侧「已提交」 + 字段转只读 |

约束：

- **「需要你的回复」只出现在当前对话最后一轮、且用户还没回复的追问上。** 历史追问后面已有用户消息，就不再提示——否则用户会反复回到已经处理完的地方。数据里的类型标记不足以判定，必须结合"后面是否已有用户消息"。
- 执行中的状态在**选中、悬停、聚焦时都必须保持可见**。悬停出现更多操作按钮时，Spinner 让位而不是消失。
- **只有当前运行中的过程用动画**，历史运行记录和已完成状态用静态。

〔指南〕**状态不能只依靠颜色**传达，除颜色外必有图标或文字（见 [5.3](#53-无障碍与包容性)）。

## 4.2 模拟执行的时间结构

〔通用契约〕演示或模拟流程中，执行过程要**分阶段推进**，关键环节留出等待，而不是一次性把结果拍出来。

- 阶段推进**复用真实的运行中状态**（Spinner、扫光），不另做一套。
- 尊重「减少动态效果」偏好：此时等待**压缩为立即推进**，不是保留动画只是变慢。

**为什么**：执行的时间感是可信度的一部分。瞬间完成的复杂任务看起来像假的。

> 这条直接影响 mock 剧本的编排方式：剧本要能表达"分阶段推进 + 每阶段延时"，不能只是一次性输出全部内容。

## 4.3 动效原则

〔通用契约〕

- 只用于**解释空间关系和状态变化**，不用于装饰。
- 折叠展开用高度/透明度过渡；**收起态要真正不可交互、不可聚焦**，不能让隐藏内容拿到键盘焦点（需 `aria-hidden` + `inert` + 禁用指针事件）。
- 面板打开滑入、关闭留出退出时间；但**切换对话必须立即清理**，绝不能短暂展示上一个对话的产物。
- **拖拽过程中不加过渡动画。**
- 所有动效尊重「减少动态效果」偏好（`prefers-reduced-motion`）。
- **同一种效果全局只有一个实现**，不要并存两套关键帧。

# 五、全局规则

## 5.1 风险分级与人工接管

〔指南〕风险分级用于判断"智能体能不能直接做"；需要确认时交互方式见 [3.4](#34-操作确认)。

| 风险等级 | 判定条件 | 示例 | 处理要求 | 日志要求 |
|---|---|---|---|---|
| **低** | 只读，不写入、无实际后果 | 查制度、总结文档、生成草稿预览 | 直接执行，执行后给结果 | 记录基础运行日志 |
| **中** | 创建/修改个人范围内、可撤销的数据 | 建日程、存草稿、生成待办 | 执行前轻量确认，展示关键字段 | 记录关键输入、结果和用户确认 |
| **高** | 影响他人/资金/权限/正式数据，或不可轻易撤销 | 发邮件、提交审批、删除、改权限、付款 | **强确认**（确认按钮/页，非自然语言）；展示对象/动作/影响范围/后果/操作人；**不得静默执行** | 完整审计留痕（对象/动作/操作者/时间/结果） |

**判定口诀**：

```
会不会影响"别人 / 钱 / 权限 / 正式数据 / 不可撤销"？
- 会 → 高风险
- 只动"自己范围内、可撤销"的数据 → 中风险
- 只读、不落库 → 低风险
```

**落地要点**：
- 写操作及高风险跨系统操作**不得静默执行**；只读操作应明确展示调用状态。
- 无权限/结果不可验证时**不自动执行**。
- 智能体能力不足、权限受限、结果无法验证、或任务必须由人工承担责任时，**停止自动执行并提供人工接管入口**；交接时保留用户意图、上下文、已完成步骤及异常原因。

## 5.2 异常处理

〔指南〕异常时应准确说明**当前状态、异常位置、对结果的影响**，并提供明确可执行的恢复路径。**不应仅告知"失败"，也不得在未完成时暗示已成功。**

| 场景 | ✅ 正确做法 | ❌ 错误做法 |
|---|---|---|
| 服务不可用 | 说明暂时无法提供服务，建议稍后重试 | 持续加载或只显示错误码 |
| 响应超时 | 提供继续等待、取消或重试选项 | 无限等待或自动反复重试 |
| 执行失败 | 说明失败环节，并提供重试或替代方案 | 仅提示"执行失败"或编造结果 |
| 部分完成 | 区分已完成与未完成内容，支持仅重试失败步骤 | 显示为完全成功或完全失败 |
| 权限不足 | 说明缺少的权限，并提供授权或申请入口 | 只提示"无权访问" |
| 能力不支持 | 说明能力边界，并推荐替代方案 | 编造结果或笼统提示失败 |
| 结果未知 | 说明无法确认执行结果，并引导用户核验 | 未经核验便提示成功或直接重试 |

**设计要求**：
- 异常提示说明"发生了什么、影响了什么、下一步怎么做"。
- 保留用户的提示词、附件、上下文及已生成内容，避免重复操作。
- 涉及发送/发布/支付/删除等操作时，**重试前确认上次执行结果**，避免重复执行。
- 技术错误码可作补充信息展示，**不应替代用户可理解的说明**。
- 文案**不责备用户**，并提供下一步帮助。

## 5.3 无障碍与包容性

〔指南〕
- 文本和背景必须保持最低 **WCAG AA** 对比度（正文 ≥ 4.5:1），**亮暗两套都要过**。
- AI 生成内容、工具调用状态、错误提示应能被屏幕阅读器感知。
- **流式输出不应造成重复朗读或状态混乱**（用 `aria-live="polite"` 的 `role="log"` 容器承载）。
- 图片、图表、文件类结果应提供文本摘要或替代说明。
- 移动端触控区域应足够大（**≥ 44px**），核心操作不依赖 hover。
- **键盘可完成核心操作**，焦点可见。
- 纯图标按钮必须有**可访问名称**（`aria-label`）与 Tooltip。
- **不靠颜色单独传达信息**：状态除颜色外必有图标/文字/形状。

**最小落地片段**：

```html
<!-- 纯图标按钮：真 button + aria-label -->
<button class="icon-btn" aria-label="关闭面板">✕</button>

<!-- 可选项用真 button，可键盘聚焦；选中态不只靠颜色 -->
<button class="chip" role="button" aria-pressed="true">年假 ✓</button>

<!-- 图表：role=img + 文字替代说明 -->
<div role="img" aria-label="Q2 报销金额：4月2.48万，5月3.12万(峰值)，6月3.04万">…柱状图…</div>
<p class="chart-alt">图表说明：Q2 报销金额 4/5/6 月分别为 2.48/3.12/3.04 万元。</p>

<!-- 流式/状态区：aria-live 播报，避免重复朗读 -->
<div class="stream" role="log" aria-live="polite">…</div>
```

```css
:focus-visible { outline: 2px solid var(--ring); outline-offset: 2px; } /* 可见焦点 */
.icon-btn { min-width: 44px; min-height: 44px; }                        /* 触控区 ≥44px */
```

> ⚠️ 沉浸式实测实现的无障碍覆盖偏薄（主要落实了"不靠颜色单独传达"与"纯图标按钮有可访问名"两条）。本节其余各项在整合时需要**逐组件补齐**，见 [quality-gates.md](overview/quality-gates.md) 的无障碍门禁。

# 六、视觉基础

## 6.1 颜色

〔通用契约〕**只用语义 Token**：`background` / `foreground` / `muted` / `accent` / `primary` / `primary-bg` / `sidebar-*` / `success` / `warning` / `info` / `destructive`。

- 业务组件里**不硬编码主题色，不绕过变量层**。
- 一组操作里**只有一个主操作用 `primary`**；危险操作用 `destructive`，且**不设为默认**。
- **暗色由 Token 层覆盖，组件不为暗色单独写颜色。**

完整取值表见 [theme/design-tokens.md](theme/design-tokens.md)。

## 6.2 字号阶梯

〔通用契约〕

| 用途 | 尺寸 |
|---|---|
| 对话正文 | **15px，行高 1.6** |
| 辅助信息、状态、耗时、表单只读值、过程文本 | **14px / 20px** |
| 极次要标注 | **12px** |

Markdown 正文统一由排版层处理，不在业务组件里逐个元素设样式。

## 6.3 已成契约的组件尺寸

〔沉浸式契约〕**只列已成为契约的档位。** 没写进本节的数值属于实现细节，不要当规范引用。

| 对象 | 值 |
|---|---|
| 动作 Badge | 高 32px，最大宽 300px，全圆角，`secondary` 底，悬停切 `input` 底；图标与文字颜色不变 |
| 卡片类（澄清表单等） | 最大宽 **600px**，圆角 12px |
| 深度思考面板内容 | `secondary` 底 + 边框，圆角 8px，内边距 12px |
| 桌面侧栏 / 移动抽屉 | **240px / 320px** |
| 附件卡片 | 固定宽度，与输入区上传区同款 |

**同一执行步骤里的多个动作 Badge 纵向排列，不横向并排**——横排会在窄屏折行成不可预期的形状。

## 6.4 图标

〔通用契约〕

- **全产品单一图标库**（本项目为 Lucide）。
- 上下文与能力类图标走**统一注册表**，不在各处即兴挑选（见 [components/registry/](components/registry/)）。
- **文件类型图标是普通菜单图标**：按扩展名区分形状，颜色跟随文字色，**不加彩色底**。
- **专家头像是圆形彩色标识**：同一专家的图标与颜色在任何位置都稳定；悬停/聚焦时只变行背景，**头像本身不变色**。

**区别的理由**：文件是「一类东西」，专家是「一个人格」。前者需要归类，后者需要辨识。

# 七、扩展新能力的决策流程

〔通用契约〕新增任何能力前，按顺序回答：

1. **它属于哪一层？**（[委托 / 对话 / 过程 / 产物](#02-产品心智模型与四层信息分层)）不能归位说明能力定义还没想清。
2. **它有用户可查看的产物吗？** 有 → 决定容器类型（[Tab / 蒙层](#353-产物容器区分并排比对与专注查看)）；没有 → 只做过程说明，**不做可点击**。
3. **它是消息语义的一部分吗？** 是 → 内联；否 → 附件区、操作行或[不进消息流](#311-上下文与能力按能不能内联三分)。
4. **它需要新层级吗？** 默认答案是不需要。只有真的出现「先规划再分头执行」才引入 [L2](#322-层级必须反映任务真实复杂度绝不为完整性硬造)。
5. **它的状态属于[已有四种](#41-四种状态语言)之一吗？** 是 → 复用现有表达；否 → 先补状态语言定义，再做视觉。
6. **它的图标已有归属吗？** 有 → 复用；否 → 进[统一注册表](#64-图标)，不在使用处就地挑。

回答完这六问之后，去 [overview/extension-map.md](overview/extension-map.md) 查"改哪个文件、不要碰哪个文件"。

> **前置步骤**：在走本流程之前，先判断该需求**能否用配置 + 场景数据覆盖**。能覆盖就不要改代码；不能覆盖才进入本流程并在需求文档中说明要扩展什么。详见 [SKILL.md](../SKILL.md) 的强制判断步骤。

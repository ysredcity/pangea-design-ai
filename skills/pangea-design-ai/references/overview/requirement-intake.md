# 需求规格化（生成前第一步）

**不论输入是「一句话需求」还是「完整 PRD」，生成任何实际代码之前，先转化为一份面向界面架构的需求文档并经用户确认。**

## 流程（克制、限轮）

1. **理解意图**：提取目标用户/角色、核心场景、关键实体与数据、主要操作。
2. **界面形态判定**：按 [design.md 2.1 决策树](../design.md#21-界面形态选型)判断沉浸式/助手式/嵌入式，说明判断依据（"AI 是主角还是配角"）。
3. **有限轮澄清**：只针对**影响界面架构**的模糊点提问（见下方清单）；**一次性打包成一组问，最多 1–2 轮**；仍不明确的用合理默认假设补齐并在文档标注。
4. **产出需求文档**（模板见下）。
5. **确认闸门（硬停止）**：输出需求文档后，**请用户确认并结束本轮回复**——不要在同一轮继续生成任何工程文件。

> **需求文档只是对话内容，不是产物**：直接写在回复里，**不落盘成 `.md` 工程文件、不放进产出目录、不渲染成页面**。确认后的交付物是一个可运行的智能体应用（见 [SKILL.md 第三道门](../../SKILL.md#-第三道门交付物只能是可运行的智能体应用)）。

## 澄清问题清单（按需选用）

- 核心场景与用户角色是什么？（决定界面形态选型）
- 是否需要左侧导航/资源区？（沉浸式：对话管理菜单栏是否必需；助手式：资源/项目区内容）
- 中间区域承载什么？（沉浸式对话流的话题范围；助手式主工作区是什么类型的画布/编辑器/表格）
- 是否需要右侧面板/对话辅助区？承载什么类型的制品（文档/表格/图片/代码/图表）？
- 涉及的操作风险等级——是否有高风险操作（发送/删除/支付/改权限等）需要强确认？
- 是否需要工具调用/多步任务的过程展示？
- 产品名称、智能体名称与人设（功能导向命名，避免真人化）。
- 部署/交付形式（demo 预览 or 接入现有产品）。

能按行业常规推断的（分页、四态、追问澄清基本流程、无障碍基线）不问。

## 需求文档模板

```markdown
# <产品名> 需求文档（v0）

## 1. 概述
一句话描述产品定位与核心场景。

## 2. 界面形态选型
- 选型结果：沉浸式 Agent / 助手式 Copilot（[+ 助手式子类型：三栏并列/浮窗/浮层抽屉/侧边抽屉]）
- 判断依据：<对照 design.md 2.1 决策树，说明"AI 是主角还是配角">

## 3. 区块规划
- 左侧区域：<是否需要 + 承载什么>
- 中间区域：<对话流的话题范围 / 主工作区类型>
- 右侧区域：<面板/对话辅助区承载什么制品类型>

## 4. 智能体人设
- 名称：<功能导向名称>
- 描述：<能做什么/不能做什么>

## 5. 核心场景与交互
逐场景描述：用户输入 → 智能体响应形式（Markdown/澄清卡片/确认卡片/制品卡片）→ 风险等级 → 是否需要工具调用过程展示。

## 6. 全局约定
- 数据来源：mock（PM demo）/ 真实接口（开发交付）
- 高风险操作清单（如有）
- 待确认假设

## 7. 待确认假设
列出因澄清限轮而采用的默认假设，供用户确认或修改。
```

> ⛔ **同一轮里既产出需求文档又产出工程代码是错误的**。「已确认」= 用户看到文档后的明确肯定答复；用户的初始需求、对澄清问题的回答都**不算**确认。

已确认文档下的增量迭代、纯样式/文案微调、用户显式要求"不用出文档直接做"时可跳过本步骤（从严解释）。

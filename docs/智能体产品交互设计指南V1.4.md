# 智能体产品交互设计指南



## 一、核心原则

- **准确**：工具应能感知对话上下文，支持并预测用户意图。响应和用户界面应与用户个人需求紧密相关。

- **克制**：每次交互都应聚焦于一个清晰明确的操作或结果。信息和用户界面应精简到极致，仅用于支持上下文。

- **轻量**：工具应该感觉快速轻便，从而增强对话效果，而不是让对话变得繁琐。

- **可信**：清晰说明能力边界与执行状态，确保过程可控、结果可验证。

- **普适**：设计必须支持广泛的用户群体，保证不同能力、设备和熟练度的用户都能完成核心任务。



---



## 二、用户感知

> 定义用户如何形成对智能体的整体认知，核心围绕能力识别与界面形态两大维度展开。
> 
> 

### 2\.1 能力识别

#### 角色与身份

> 定义智能体“是谁”，用户应如何理解它。

**基本原则**：

- **命名**：优先使用功能导向名称，例如“合同审核助手”、“数据分析助手”。ToC 产品因品牌运营需要可使用更具品牌感的名称，但不得使用真实人名、暗示真人身份或造成品牌混淆。

- **头像/标识**：优先使用虚拟形象、抽象图形或统一 AI 标识，避免使用真人头像。

- **描述**：明确告知用户智能体能做什么、不能做什么。

- **语气**：专业场景严谨克制，生活场景轻松自然。



**不推荐的方式**：

- ❌ 给 AI 起人名、设定性别、使用真人照片。

- ❌ 隐瞒 AI 身份让用户误以为在和人对话。

- ❌ 角色设定与实际能力不匹配，例如声称“全能”但只能做简单问答。



#### 首屏引导

> 用户进入智能体后，应快速知道“它能做什么、我可以从哪里开始”。
> 
> 

**设计要求**：

- 首次进入展示一句欢迎语、核心能力概述和 3\-5 个推荐操作。

- 推荐操作应具体、可点击，例如“总结这份会议纪要”，禁止使用"有什么可以帮你"等模糊引导语。

- 空状态应展示能力卡片、分类入口或示例任务，避免显示空白页面或仅显示Logo。

### 2\.2 界面形态

> 界面形态回答“用户主要在哪里完成任务”。界面形态的选择应由主要任务决定，而不是由是否接入 AI 决定。
> 
>

**设计特征**：

- **独立性**：界面应脱离主应用运行，不依赖外部窗口或组件；

- **专注性**：隐藏系统级通知、任务栏及无关控件，可视区域内仅保留与当前任务相关的功能入口，减少外界干扰，助力任务执行的流畅性与高效性；

- **连贯性**：支持同一语境下的连续追问；



**区块定位**：遵循“中间优先、两侧辅助”。左侧帮助用户找到任务，中间推进任务，右侧处理任务对象。

|区域|核心职责|
|---|---|
|左侧对话管理菜单栏（非必需）|管理入口、任务、项目、历史会话、智能体切换与全局导航。|
|中间对话流|承载用户意图、智能体响应、任务过程、工具调用、确认和反馈。|
|右侧独立面板|展示文档、表格、代码、图表、详情、预览、配置、引用资料等任务对象。|

**典型产品**：Kiro、Cursor、Lovart、Tapnow、多维表格、飞书APaaS等

**按照助手式与产品的布局关系，可分为以下三种类型**：

- **浮窗**：可拖拽到页面任何位置，支持拖拽尺寸。浮窗遮挡原页面内容，不适合需要与主页面对照操作的场景；

- **浮层抽屉**：压缩原页面空间，容器占据页面中右/左侧一部分，与主页面信息共用一个顶部导航。内容无遮挡，适合需要与主页面信息对照，或频繁交互的场景；

- **侧边抽屉**：压缩原页面空间，容器占据页面中右/左侧一部分，与主页面信息形成左右两部分布局。不适用于主页面信息密度大、横向空间紧张界面类型。



**区块定位**：采用“左侧资源/项目区 \+ 中间主工作区 \+ 右侧对话辅助区”的三区结构（部分专业工具会使用浮层、抽屉等，但不应遮挡主工作对象）。

|区域|核心职责|
|---|---|
|左侧资源/项目区|管理文件、图层、数据源、页面、任务树、项目目录、历史版本或业务对象列表。|
|中间主工作区|承载用户主要操作对象，例如画布、代码编辑器、表格、设计稿、数据看板、业务详情页。|
|右侧对话辅助区|承载意图输入、任务解释、工具调用过程、建议方案、局部确认和与当前对象相关的 AI 操作。|

**典型产品**：飞书文档、Figma、Notion、Photoshop、多维表格等部分场景功能

**设计特征**：

- **灵活触发**：用悬浮卡片、划词工具栏或右键菜单形式出现，能随时触发的低覆盖容器；

- **上下文保留**：卡片关闭后，宿主编辑器须保持完整；

- **权限最小化**：仅申请完成当前任务所需的最小宿主权限（如当前选中文本读取权限）；



#### 如何选择

```Markdown
**主要任务是什么？**（由任务决定，不由"是否接入 AI"决定）
├─ **用自然语言表达目标、等待结果，需要专注连贯环境**
│     → **沉浸式 Agent**（左菜单 / 中对话流 / 右面板）  例：通用助手、客服、问答
├─ **围绕画布/代码/表格/设计稿/业务对象持续操作，AI 辅助但不想离开主工作区**
│     → **助手式 Copilot**（左资源区 / 中主工作区 / 右对话辅助区；或浮窗/抽屉）  例：IDE、设计、BI、合同审阅
└─ **在现有工作流里要轻量即时的 AI（翻译/润色），无需独立对话空间**
       → **嵌入式 Embedded**（划词工具栏/悬浮卡/右键菜单）  例：文档、表格内嵌
```

> **一句话选型**："AI 是主角还是配角？配角就别抢主工作区。" 
> 
> **❌ 反例**：为塞 AI 侧栏把合同正文压到一半宽 → 违反"不为放置 AI 入口压缩主要业务对象"。

## 三、场景链路

> 对话过程定义智能体如何与用户协作完成任务。

### 3\.1 意图输入

意图输入是用户向智能体表达目标并配置执行条件的统一入口，由 **提示词、上下文、能力** 三类要素共同构成。设计上应支持三类要素独立输入、组合使用和随时编辑，并在发送前清晰呈现当前意图的完整构成。

|输入要素|**内容范围**|**设计要求**|**推荐交互**|
|---|---|---|---|
|提示词<br>|用户的目标、要求、约束、输出格式等|提示词是意图输入的核心载体，应支持多行编辑、连续补充、撤销修改和草稿保留；除键盘输入外，还应支持语音转写等录入方式，并允许用户在发送前校对和修改|1. 键盘输入<br>2. 语音输入|
|上下文|附件、引用、知识库、记忆等与任务相关的信息|上下文应结合实际场景进行精细化设计，明确来源、作用范围、有效期限和权限状态；已添加的上下文应以标签或卡片形式展示，支持预览、替换和移除，并区分本次使用的临时上下文与可持续使用的记忆内容|1. 使用 @ 呼出上下文选择器<br>2. 添加按钮/菜单|
|能力|子智能体、技能、工具等可调用的执行能力|能力应根据当前任务提供推荐和主动选择两种方式，并在调用前展示名称、用途、适用范围及可能产生的影响；已选择的能力应在输入区域内显式呈现，避免用户误以为系统会自动调用所有能力|1. 使用 / 呼出能力选择器<br>2. 添加按钮/菜单|

**设计要求**：

- 输入区域应作为统一的意图编排空间，支持提示词、上下文和能力的混合编辑；

- 使用**`@`** 和 **`/`** 时，应提供可搜索、可分组、支持最近使用记录的选择面板，并在选中后将对象以可识别的标签插入输入区域；

- 能力快捷入口可根据常见任务提供推荐项，例如 PPT、文档、数据分析、视频、图像和产品开发；推荐项应作为快捷选择，不替代用户对具体能力的控制；

- 占位提示应根据当前场景动态变化，说明可输入的任务类型及可使用的快捷方式；语音转写、文件上传、上下文解析等异步操作应展示处理中、成功和失败状态；

- 对于涉及敏感数据、外部系统或高风险操作的上下文和能力，应在发送前补充权限、范围或审批提示；

### 3\.2 信任透传

智能体执行任务时，应让用户知道“正在发生什么”。以决策过程可见、加载状态可感、结果来源可查为基本原则，在全链路提升用户对智能体输出结果的信任度。

#### 任务过程

以用户可理解的方式展示当前任务状态、关键步骤、工具调用和阶段性结果，不展示模型内部的原始思维链或系统提示词。包含以下 3 个层级的过程信息：

- **状态层**：明确展示本轮对话智能体执行所处的状态和消耗时长；

- **任务层（非必须）**：长链路任务应以有序列表逐条展示规划后的核心任务名称、状态；

- **执行层**：渐进式展示任务步骤、工具调用、检索范围及阶段性结果；

### 3\.3 追问澄清

用户意图模糊时，智能体应主动追问，而不是猜测执行。

> **展示方式**：Markdown、澄清卡片
> 
> 



**需要澄清的情况**：

- 用户输入过短，且可能对应多种操作。

- 关键参数缺失，导致任务无法执行，例如“帮我发邮件”但没有收件人。

- 出现歧义词，例如“最新的”“重要的”“那个文件”。

- 操作风险较高，可能影响真实业务数据。

**设计要求**：

- **追问数量规则：**每次追问只问关键缺口，不要把所有缺失项一次性甩给用户。

- **追问呈现方式：**待澄清事项 ≤ 2 → 自然语言追问；\> 2 → 澄清卡片；澄清事项需要枚举→ 澄清卡片；

- **表单录入方式：**选择优于输入，可基于追问的事项生成几个可行的选项，并按需提供“其他”、“都不适用”这类选择；

- **跳过机制：**任何追问方式都应允许用户“跳过/忽略”；

- **等待状态：**对话处于追问状态时，应置于“等待”状态，需要在对话入口位置（如对话列表）有明确的状态呈现，直至用户完成澄清提交；

- **意图修正：**用户应能随时修正已表达的意图；

**对话过程总体需遵循以下原则**：

- **简洁**：默认回答用户当前问题，用户要求详细时再展开。

- **连贯**：保持上下文，不要求用户重复已提供的信息。

- **可控**：用户应能停止、修改、重试或继续追问。



#### 澄清卡片

澄清卡片用于采集多个必要参数，避免多轮追问造成碎片化体验。

**设计要求**：

- 无 Tabs、Menu 等深层导航，无内部滚动；

- 表单不超过 10 个，优先单列排布；

- 仅对阻断性内容设置必填；

- 操作按钮放置在卡片底部，从左至右、从上至下排列，数量不超过 3 个，主按钮不超过 1 个；

**结构模板**：

```Plain Text
┌─ 卡片名称 ───────────────────────┐
│ [字段1] ● 选项A  ○ 选项B  ○ 选项C  (选择优于输入) │
│ [字段2] ● 选项A  ○ 其他：____                    │
│ [字段3] ○ …            (单列优先，字段 ≤10)       │
│ ───────────────────────────  │
│ [ 主操作 ] [ 重置 ] [ 跳过 ]                      │  ← 按钮≤3，主按钮≤1
└─────────────────────────────┘
```

### 3\.6 消息操作

## 四、全局设计规则

### 4\.1 风险分级与人工接管

风险控制用于判断“智能体能不能直接做”，需要用户确认时，具体交互方式见“[3\.4 操作确认](https://hisense.feishu.cn/wiki/RmSbwHgfuiUyMrkNoi4cJCBsnQg#share-DALVd7bDmontFPx52FjcKLJnnjf)”。

**操作风险分级**：

|**风险等级**|**判定条件**|**示例**|**处理要求**|**日志要求**|
|---|---|---|---|---|
|低|只读，不写入、无实际后果|查制度、总结文档、生成草稿预览|直接执行，执行后给结果|记录基础运行日志|
|中|创建/修改个人范围内、可撤销的数据|建日程、存草稿、生成待办|执行前轻量确认，展示关键字段|记录关键输入、结果和用户确认|
|高|影响他人/资金/权限/正式数据，或不可轻易撤销|发邮件、提交审批、删除、改权限、付款|强确认（确认按钮/页，非自然语言）；展示对象/动作/影响范围/后果/操作人；不得静默执行|完整审计留痕，包括对象、动作、操作者、时间和结果|

```Markdown
会不会影响"别人 / 钱 / 权限 / 正式数据 / 不可撤销"？
- 会 → 高风险；
- 只动"自己范围内、可撤销"的数据 → 中风险；
- 只读、不落库 → 低风险；
```

**落地要点**：

- 写操作及高风险跨系统操作不得静默执行；只读操作应明确展示调用状态；

- 无权限/结果不可验证时不自动执行；

- 当智能体能力不足、权限受限、结果无法验证或任务必须由人工承担责任时，应停止自动执行并提供人工接管入口；交接时应保留用户意图、上下文、已完成步骤及异常原因；



### 4\.2 异常处理

智能体出现异常时，应准确说明当前状态、异常发生的位置及对任务结果的影响，并提供明确、可执行的恢复路径。异常提示不应仅告知“失败”，也不得在实际未完成时暗示任务已经成功。

|场景|**✅ **正确做法|**❌ **错误做法|
|---|---|---|
|**服务不可用**|说明暂时无法提供服务，建议稍后重试|持续加载或只显示错误码|
|**响应超时**|提供继续等待、取消或重试选项|无限等待或自动反复重试|
|**执行失败**|说明失败环节，并提供重试或替代方案|仅提示“执行失败”或编造结果|
|**部分完成**|区分已完成与未完成内容，支持仅重试失败步骤|将部分完成显示为完全成功或完全失败|
|**权限不足**|说明缺少的权限，并提供授权或申请入口|只提示“无权访问”|
|**能力不支持**|说明能力边界，并推荐替代方案|编造结果或笼统提示失败|
|**结果未知**|说明无法确认执行结果，并引导用户核验|未经核验便提示成功或直接重试|

**设计要求**：

- 异常提示应说明“发生了什么、影响了什么、下一步怎么做”；

- 保留用户的提示词、附件、上下文及已生成内容，避免重复操作；

- 涉及发送、发布、支付、删除等操作时，重试前应确认上次执行结果，避免重复执行；

- 技术错误码可作为补充信息展示，不应替代用户可理解的说明；



### 4\.3 响应式适配

本章定义不同设备和屏幕条件下的适配要求。界面形态的定义见 [2\.2](https://hisense.feishu.cn/wiki/LHnzwohSgiWJp1k7tY5cjbsGn7d?renamingWikiNode=false#share-ZKFMdG1Joocw1fxtEuecpOeqnqf)。

**核心原则**：

- **优先保障主任务**：沉浸式优先保障对话流，助手式优先保障工作区。

- **保留上下文**：布局变化不应导致会话、输入内容、打开对象丢失。

- **收纳辅助区**：空间不足时，优先收起左侧导航，再将右侧面板转为覆盖式或全屏式。

- **简化小屏体验**：屏幕越小，越应减少并列区域和复杂浮层。



**适配要求**：

> **降级顺序铁律：先收左侧菜单栏 → 再把右侧面板降级为覆盖/全屏。**（优先保主任务：沉浸式保对话流，助手式保工作区。）
> 
> 

|设备|标准断点|要求|
|---|---|---|
|桌面端|≥1024px|多栏并列；对话流/主工作区保持可读可操作|
|平板端|≥768px|左侧菜单默认收起（抽屉）；双栏或模式切换|
|移动端|＜768px|单栏任务流；面板升级为全屏/底部弹层；输入框、停止生成、返回、关闭面板等关键操作稳定可达|

### 4\.4 无障碍与包容性

智能体产品应保证不同能力、设备和熟练度的用户都能完成核心任务。

**核心要求**：

- 文本和背景必须保持最低 WCAG AA 对比度。

- AI 生成内容、工具调用状态和错误提示应能被屏幕阅读器感知。

- 流式输出不应造成重复朗读或状态混乱。

- 图片、图表、文件类结果应提供文本摘要或替代说明。

- 移动端触控区域应足够大，核心操作不依赖 hover。

- 文案不应责备用户，应提供下一步帮助。

**最小落地片段**：

```HTML

<button class="icon-btn" aria-label="关闭面板">✕</button>

<!-- 可选项用真 button，可键盘聚焦；选中态不只靠颜色 -->
```

### A\. 术语表

|术语|定义|
|---|---|
|Agent / 智能体|能够理解意图、自主规划并调用工具执行任务的 AI 系统。|
|AI 助手|以问答、建议、内容生成等方式辅助用户完成工作的 AI 产品形态。|
|Copilot|嵌入业务流程或专业工具中，辅助用户完成任务的 AI 能力。|
|Tool Call / 工具调用|AI 调用外部系统、接口、插件或本地能力完成特定操作。|
|Streaming / 流式输出|AI 逐步生成内容并实时展示。|
|Conversation Starter / 对话启动器|预设的推荐操作，用于帮助用户开始第一次交互。|
|意图澄清|用户意图模糊时，AI 主动追问，而非猜测执行。|
|推荐追问|每次交互结束后提供的 2\-4 个基于上下文的后续建议。|
|内联响应|响应内容直接嵌入对话流。|
|面板响应|响应内容在独立面板中承载，用于复杂查看或操作。|
|制品|AI 生成的文档、表格、图片、代码、报告等可独立处理的结果。|
|人工接管|AI 无法或不应继续处理时，将任务交由人工处理。|

### B\. 设计自查模板

|分类|审查项|
|---|---|
|价值与边界|* [ ] 用户能在 3 秒内知道这个智能体能做什么。<br>* [ ] 智能体名称、头像和身份声明不会让用户误以为是真人。<br>* [ ] 能力边界清晰，没有"全能化"表达。<br>* [ ] 首屏展示欢迎语、核心能力概述和 3\-5 个推荐操作，推荐操作具体可点击，未使用"有什么可以帮你"等模糊引导语。<br>* [ ] 空状态展示了能力卡片、分类入口或示例任务，未显示空白页面或仅显示 Logo。|
|输入与意图|* [ ] 支持文本、语音、文件/图片等多模态输入，各有清晰的状态和错误处理。<br>* [ ] 智能填充的补全内容高亮展示，支持逐条确认。<br>* [ ] Prompt/Skill/Agent 推荐名称表达用途，已选项可见且可取消。<br>* [ ] 意图模糊时主动追问而非猜测执行；追问事项 ≤2 个时用自然语言，\>2 个时切换为澄清卡片。<br>* [ ] 任何追问方式都允许用户跳过/忽略；追问期间对话入口有明确的等待状态。|
|对话与任务|* [ ] AI 回复默认简洁，没有无关延伸。<br>* [ ] 长任务以有序列表展示关键步骤、执行状态和阶段性结果，不展示模型内部推理过程。<br>* [ ] 工具调用展示对用户可理解（如"正在读取 4 份文档"而非接口名）。<br>* [ ] 结果来源记录了支撑答案的证据，建立了与原始信息源的可追溯关联。<br>* [ ] 失败后有重试、修改输入或降级方案。|
|内容呈现与布局|* [ ] 界面形态（沉浸式/助手式/内嵌式）符合主要任务，未为了 AI 入口牺牲主工作区。<br>* [ ] Markdown、澄清卡片、确认卡片、制品卡片使用场景清晰。<br>* [ ] 制品卡片在对话流内只展示摘要，点击后在独立面板打开，面板操作结果同步回对话流。<br>* [ ] 交互结束后提供 2\-4 个基于上下文的推荐追问，且避开了不应触发的场景（用户不满、任务失败等）。<br>* [ ] 移动端已将多栏结构折叠为单栏任务流，输入框、停止生成、返回对话、关闭面板等关键操作稳定可达。|
|风险与可信|* [ ] 操作风险已分级（低/中/高），写操作、高风险操作不得静默执行。<br>* [ ] 高风险确认使用了确认按钮或确认页（非自然语言确认），展示了对象、动作、影响范围和后果。<br>* [ ] 明确标识 AI 身份，不伪装成人或最终责任人。<br>* [ ] 权限不足、敏感信息、跨系统调用有明确提示。<br>* [ ] 重要结果可溯源，AI 不确定时会说明限制。<br>* [ ] 高风险确认、工具调用、文件生成、导出、人工接管等关键行为已留痕。<br>* [ ] 存在人工接管入口和上下文交接机制。|
|无障碍|* [ ] 文本和背景满足最低 WCAG AA 对比度。<br>* [ ] 键盘可完成核心操作。<br>* [ ] 屏幕阅读器可读取对话内容和状态变化，流式输出未造成重复朗读或状态混乱。<br>* [ ] 移动端触控区域满足可用性要求，核心操作不依赖 hover。<br>* [ ] 图片、图表、文件结果有文本摘要或替代说明。<br>* [ ] 文案不责备用户，并提供下一步帮助。|
